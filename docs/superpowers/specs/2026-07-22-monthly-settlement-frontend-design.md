# 월별 정산 조회 프론트엔드 반영 설계

- 작성일: 2026-07-22
- 백엔드 기준: `beadv6_6_3JMT_BE`의 `#481 (PR)`
- 대상 화면: 판매자 `/shop`, 관리자 `/admin/settlements`

## 1. 배경

백엔드 `#481 (PR)`에서 판매자와 관리자의 정산 목록 응답이 주간 정산 행 단위에서 월별 집계 단위로 변경됐다. 월별 목록은 금액 합계와 상태별 주간 정산 건수를 제공하고, 새 상세 API는 해당 월에 속한 주간 정산 전체와 각 주간 정산에서 수행 가능한 액션을 제공한다.

현재 프론트엔드는 목록 응답을 주간 정산으로 해석해 한 행에서 상태와 액션을 표시한다. 이 구조로는 새 응답 계약을 표시할 수 없고, 액션 대상인 주간 정산 ID도 월별 목록에 존재하지 않는다. 따라서 두 화면을 월별 요약 목록과 주간 상세 아코디언 구조로 변경한다.

관리자 정산 화면의 실제 도메인은 결제가 아니라 정산이므로 `/admin/payments` 경로와 `payments` 네이밍도 `/admin/settlements`와 `settlements`로 바꾼다.

## 2. 목표와 제외 범위

### 목표

- 판매자와 관리자 정산 목록을 월별 집계 응답 계약에 맞춘다.
- 월별 행을 펼치면 주간 정산 상세를 지연 조회해 같은 화면에 표시한다.
- 지급 신청과 관리자 상태 전이는 주간 정산의 `settlementId`와 `availableActions`를 기준으로 실행한다.
- 판매자와 관리자 화면에 월 선택 필터를 제공한다.
- 관리자 요약 카드는 선택한 월을 기준으로 조회한다.
- 관리자 정산 경로를 `/admin/settlements`로 바꾸고 기존 `/admin/payments`는 새 경로로 리다이렉트한다.
- API 응답 변환과 화면 상태를 역할별 컴포넌트에서 분리해 테스트 가능한 경계를 만든다.

### 제외

- 백엔드 API와 정산 상태 전이 규칙 변경
- 판매자 누적 수익 요약의 의미 변경
- 월별 집계 결과를 프론트에서 다시 계산
- 판매자와 관리자 화면을 하나의 범용 정산 테이블로 통합
- 새로운 컴포넌트 테스트 프레임워크 도입
- 관리자 정산과 무관한 결제 도메인 파일의 일괄 이름 변경

## 3. 화면 구조

### 3.1 공통 탐색 방식

두 화면은 월별 목록을 먼저 보여주고 한 번에 한 월만 펼치는 인라인 아코디언을 사용한다. 월별 행에는 다음 정보를 표시한다.

- 정산 월
- 전체 주간 정산 건수와 합계 반영 건수
- 판매 건수
- 총 거래액, 수수료, 환불 차감액, 지급액
- 상태별 주간 정산 건수

월별 행을 펼치면 상세 API를 호출해 주간 정산을 기간 시작일 오름차순으로 표시한다. 이미 조회한 상세는 화면에 머무는 동안 월별로 캐시하며, 다른 월을 펼치면 기존 월은 닫는다.

`CANCELLED` 주간 정산은 상태 건수와 상세 이력에는 보이지만 백엔드가 계산한 월별 금액 합계에는 포함되지 않는다. 프론트는 이 합계를 재계산하지 않고 응답값을 그대로 표시한다.

### 3.2 판매자 `/shop`

기존 내 상점의 `정산 내역` 탭은 유지한다. 정산 탭 내부를 월 선택 필터, 상태 필터, 월별 목록, 주간 상세 아코디언으로 분리한다.

주간 상세는 `availableActions`에 `REQUEST_PAYOUT`이 있을 때만 지급 신청 버튼을 표시한다. 액션 성공 후 현재 월 상세, 월별 목록, 판매자 누적 요약을 다시 조회한다. 판매자의 누적 수익 카드는 월 선택과 무관하게 기존 전체 누적값을 유지한다.

### 3.3 관리자 `/admin/settlements`

기존 `app/admin/payments` 구현을 `app/admin/settlements`로 이동하고 관리자 메뉴 링크와 페이지 메타데이터도 새 경로를 사용한다. `app/admin/payments/page.tsx`는 UI를 중복 유지하지 않고 `/admin/settlements`로 리다이렉트한다.

관리자 목록은 판매자명과 정산 월을 함께 표시한다. 주간 상세의 액션 버튼은 프론트 상태표가 아니라 백엔드 `availableActions`를 기준으로 노출하고, 액션 타입을 기존 PATCH 경로에 매핑한다. 취소는 기존 확인 다이얼로그를 유지한다.

관리자 요약 API에는 선택한 `settlementMonth`를 전달한다. 상태 필터는 해당 상태가 하나 이상 포함된 월 그룹을 찾는 조건이며, 선택된 월 그룹의 합계와 `statusCounts`는 월 전체 기준임을 UI에서도 유지한다.

## 4. 코드 구조

### 4.1 API와 계약

`lib/settlements.ts`는 HTTP 호출과 공개 타입을 제공하고, 응답 변환은 별도 순수 함수 모듈로 분리한다.

책임은 다음과 같다.

- 월별 목록, 월별 상세, 상태 건수, 주간 정산, 액션 타입 정의
- 문자열 또는 숫자로 오는 금액을 `number`로 정규화
- 판매자·관리자 월별 목록 응답 변환
- 판매자 `GET /api/v2/sellers/me/settlements/months/{settlementMonth}` 호출
- 관리자 `GET /api/v2/admin/settlements/sellers/{sellerId}/months/{settlementMonth}` 호출
- 목록 요청의 `settlementMonth`, `status`, `page`, `size` 전달
- 관리자 요약 요청의 선택적 `settlementMonth` 전달
- 주간 액션 타입과 기존 PATCH 경로 매핑

백엔드 응답의 `statusLabel`과 액션 `label`을 우선 사용한다. 로컬 상태 라벨 맵은 필터와 예외적인 폴백에만 사용한다.

### 4.2 역할별 컴포넌트

판매자와 관리자는 열 구성과 액션 권한이 다르므로 각 화면 아래에 정산 전용 컴포넌트를 둔다. 공통화는 타입, 응답 변환, 금액·날짜 포맷처럼 역할과 무관한 부분으로 제한한다.

- 판매자: 월 필터, 월별 목록, 주간 상세, 지급 신청 상태
- 관리자: 월·상태 필터, 요약 카드, 월별 목록, 주간 상세, 상태 전이와 취소 확인

페이지는 인증 상태와 초기 로딩을 조정하고, 정산 컴포넌트는 목록·상세·액션 상태를 관리한다.

## 5. 데이터 흐름

1. 화면 진입 시 월별 목록 첫 페이지를 조회한다.
2. 관리자는 같은 시점에 선택 월 기준 요약을 조회하고, 판매자는 기존 누적 요약을 조회한다.
3. 월 또는 상태 필터를 바꾸면 펼친 월과 상세 오류를 초기화하고 목록을 첫 페이지부터 다시 조회한다.
4. 월별 행을 펼치면 해당 역할의 월 상세 API를 호출한다.
5. 상세 조회가 성공하면 월별 캐시에 저장하고 주간 행을 표시한다.
6. 주간 액션이 성공하면 현재 월의 상세 캐시를 무효화하고 상세, 목록, 관련 요약을 다시 조회한다.
7. `더 보기`는 주간 행 수가 아니라 월 그룹 수를 기준으로 다음 페이지를 이어 붙인다.

동일한 월을 다시 클릭하면 아코디언만 닫고 캐시는 유지한다. 다른 월을 펼치면 기존 월을 닫고 새 월 상세를 표시한다.

## 6. 오류와 동시성 처리

- 목록 조회 중에는 목록 영역에 로딩 상태를 표시한다.
- 목록 조회 실패 시 빈 목록으로 오인하지 않도록 오류 안내와 재시도 버튼을 표시한다.
- 상세 조회 실패는 해당 아코디언 내부에만 표시해 다른 월 목록을 유지한다.
- 상세 `404`는 해당 월의 정산이 사라진 것으로 안내하고 목록을 새로 조회한다.
- 액션 실패는 백엔드 메시지를 다이얼로그로 표시하고 현재 월 상세를 다시 조회한다.
- 처리 중인 주간 정산의 액션 버튼만 비활성화해 중복 요청을 막는다.
- 필터 변경이나 빠른 아코디언 전환으로 이전 요청이 늦게 끝나더라도 현재 선택 상태를 덮어쓰지 않도록 요청 시점의 키를 확인한다.

## 7. 라우팅과 호환성

- 관리자 메뉴의 정산 링크는 `/admin/settlements`를 사용한다.
- 관리자 레이아웃의 페이지 메타데이터도 `/admin/settlements`를 기준으로 변경한다.
- 기존 `/admin/payments`는 Next.js의 서버 리다이렉트로 `/admin/settlements`에 연결한다.
- 주문 결제 이력처럼 실제 payment 도메인을 표현하는 파일과 경로는 변경하지 않는다.

## 8. 테스트와 검증

현재 프로젝트의 `node:test` 방식을 유지한다. 구현 전에 계약 테스트를 먼저 작성하고 실패를 확인한다.

순수 함수 테스트 범위는 다음과 같다.

- 판매자·관리자 월별 목록 응답 변환
- 월 상세의 주간 정산과 `availableActions` 변환
- 문자열 금액의 숫자 정규화
- `statusCounts`, 취소 포함 건수, 취소 제외 합계 필드 보존
- 목록 요청에서 `period` 대신 `settlementMonth` 사용
- 관리자 요약 요청에 선택 월 전달
- 관리자 주간 액션 타입과 PATCH 경로 매핑

최종 검증은 다음 순서로 수행한다.

1. 관련 `node --experimental-strip-types --test` 테스트
2. 전체 `lib/*.test.ts` 테스트
3. `npm run lint`
4. `npm run build`
5. 로컬 개발 서버에서 `/shop`, `/admin/settlements`, `/admin/payments` 리다이렉트 스모크 확인

## 9. 완료 기준

- 판매자와 관리자 정산 목록이 월별 그룹으로 표시된다.
- 월별 행을 펼치면 해당 월의 주간 정산과 가능한 액션이 표시된다.
- 월·상태 필터와 월 그룹 기준 페이지 처리가 백엔드 계약대로 동작한다.
- 주간 액션 후 목록, 상세, 요약이 최신 서버 상태로 갱신된다.
- 관리자 정산 화면은 `/admin/settlements`에서 제공되고 `/admin/payments`는 새 경로로 이동한다.
- 계약 테스트, 전체 기존 테스트, ESLint, Next.js 빌드가 통과한다.
