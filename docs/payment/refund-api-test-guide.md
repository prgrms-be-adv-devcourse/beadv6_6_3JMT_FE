## T1. 결제 내역 목록 조회

**목적**: 결제 탭이 올바른 API를 호출하고 데이터를 렌더링하는지 확인

1. 로그인 후 `/mypage` 접속
2. 사이드바에서 **결제 내역** 탭 클릭
3. 확인 항목:
   - 로딩 스켈레톤이 잠깐 표시된 후 목록이 나타나는지
   - 아래 4개 항목이 모두 보이는지

   | 상품명 | 금액 |
   |--------|------|
   | 사진 같은 제품 목업 생성기 | 5,900원 |
   | 전환율 높이는 랜딩 카피 작성 | 4,900원 |
   | 30일 SNS 콘텐츠 캘린더 | 3,900원 |
   | 코드 리뷰 자동화 봇 | 8,900원 |

4. DevTools → Network 탭 열기 → 결제 내역 탭 재클릭
   - `/api/v1/orders/payments` 요청이 보이는지
   - `/api/v1/orders` 와 **별개로** 호출되는지 (두 요청이 각각 존재해야 함)

## T2. paymentStatus별 배지 렌더링

**목적**: 상태별 배지 색상과 환불 버튼 노출 조건 확인

결제 내역 탭에서 각 행을 확인한다:

| 상품명 | 기대 배지 | 배지 색 | 환불 버튼 |
|--------|-----------|---------|-----------|
| 사진 같은 제품 목업 생성기 | 결제완료 | 파란색 | **환불 신청 버튼 있음** (`isRefundable: true`) |
| 전환율 높이는 랜딩 카피 작성 | 결제완료 | 파란색 | `—` (버튼 없음, `isRefundable: false`) |
| 30일 SNS 콘텐츠 캘린더 | 환불 신청 중 | 빨간색 | `—` (버튼 없음) |
| 코드 리뷰 자동화 봇 | 환불 완료 | 회색 | `—` (버튼 없음) |

> 결제완료(PAID) 상태이더라도 `isRefundable: true`인 경우에만 환불 신청 버튼이 노출되어야 합니다.

## T3. 환불 요청 플로우

**목적**: 환불 신청 → 즉시 상태 전환 → 재진입 시 유지 확인

### 시나리오 A — 정상 환불 신청

1. "사진 같은 제품 목업 생성기" 행의 **환불 신청** 버튼 클릭
2. 확인 모달이 열리는지 확인
3. 모달에서 **환불 신청** 확인 버튼 클릭
4. 즉시 해당 행의 배지가 **"환불 신청 중"(빨간색)** 으로 바뀌고 버튼이 `—`로 변하는지 확인

### 시나리오 B — 모달 취소

1. 환불 신청 버튼 클릭 → 모달 열림
2. **취소** 버튼 클릭
3. 상태 변화 없이 그대로인지 확인

### 시나리오 C — 탭 재진입 후 상태 유지

1. 시나리오 A 완료 후 **구매한 프롬프트** 탭으로 이동
2. 다시 **결제 내역** 탭으로 돌아오기
3. API 재호출 후 "환불 신청 중" 상태가 유지되는지 확인
   - Network 탭에서 `/api/v1/orders/payments` 재요청 확인

## T4. 에러 처리

**목적**: 에러 코드별 토스트 메시지가 정확히 표시되는지 확인

`mocks/handlers/payments.ts`의 환불 핸들러를 임시 수정하여 에러를 강제 반환한다.

```ts
// POST /api/v1/payments/:paymentId/refund 핸들러 내부
// 아래 한 줄을 추가해서 원하는 에러를 강제 반환한다
return err('PAY004', '환불 불가 상태입니다.', 400);
```

| 에러 코드 | HTTP | 기대 토스트 메시지 |
|-----------|------|--------------------|
| `PAY004` | 400 | "이미 환불 처리된 결제예요" |
| `PAY005` | 404 | "결제 정보를 찾을 수 없어요" |
| `PAY006` | 403 | "본인 결제 건이 아니에요" |
| 기타 | 500 | "환불 신청에 실패했어요. 다시 시도해주세요" |

각 케이스 테스트 방법:
1. 핸들러에 `return err('PAY004', ..., 400);` 추가 → 저장 → 환불 신청 → 토스트 확인
2. 코드를 `PAY005`, `PAY006`, `UNKNOWN`(500)으로 바꿔가며 반복
3. 어느 케이스에서도 해당 행 상태가 변하지 않아야 함

> **테스트 후 핸들러를 원래 상태로 되돌린다.**

## T5. 페이지네이션 ("더 보기")

**목적**: 추가 데이터 로드 동작 확인

기본 size=20이라 user-1의 4개 항목으로는 "더 보기"가 나타나지 않는다.
`mocks/handlers/payments.ts`에서 size를 강제로 2로 제한해 테스트한다:

```ts
// GET /api/v1/orders/payments 핸들러 내부
const page = Number(url.searchParams.get('page') ?? 1);
const size = 2; // 테스트용 — 페이지당 2개로 강제
```

1. 결제 내역 탭 진입 → 항목 **2개만** 보이고 하단에 **"더 보기"** 버튼이 보이는지 확인
2. **더 보기** 클릭 → 추가 항목 2개가 기존 목록 **아래에 append** 되는지 확인 (전체 교체 X)
3. 총 4개 = 마지막 페이지 → **"더 보기"** 버튼이 **사라지는지** 확인

> **테스트 후 `const size = 2;` 줄을 제거한다.**

## T6. 회귀 확인

**목적**: 변경 사항이 다른 탭에 영향을 주지 않았는지 확인

### 구매한 프롬프트 탭

1. **구매한 프롬프트** 탭 진입
2. 기존과 동일하게 카드 3개가 렌더링되는지 확인:
   - 사진 같은 제품 목업 생성기
   - 전환율 높이는 랜딩 카피 작성
   - 30일 SNS 콘텐츠 캘린더

### 구매 탭 잠금 오버레이 (크로스탭 연동)

1. T3 시나리오 A에서 환불 신청 완료 후 **구매한 프롬프트** 탭으로 이동
2. "사진 같은 제품 목업 생성기" 카드에 **회색 오버레이와 잠금 아이콘**이 표시되는지 확인
3. 해당 카드는 클릭 불가 상태여야 함

### 찜한 프롬프트 탭

1. **찜한 프롬프트** 탭 진입
2. 영향 없이 기존과 동일하게 표시되는지 확인
